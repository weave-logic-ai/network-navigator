# Script Reference

All agent scripts live in `agent/network-navigator/skills/linkedin-prospector/scripts/`. There are exactly **four** of them -- every one is a thin REST client against the app's API at `http://localhost:3750` (override with `NETWORKNAV_URL`). None of them touch the filesystem for contact data, run a browser, or maintain local state.

<Callout type="info">
Earlier versions of this skill shipped 17 scripts that ran Playwright against LinkedIn directly and stored data in local JSON files (`contacts.json`, `graph.json`, `icp-config.json`, and friends). That architecture was retired. The retired scripts are preserved for reference under `agent/network-navigator/.v1-archive/` but are not part of the shipped skill and are not invoked by the slash commands.
</Callout>

## The Four Scripts

| Script | Purpose | Entry point |
|--------|---------|--------------|
| `api-client.mjs` | Shared HTTP client -- not run directly | Imported by the other three |
| `configure.mjs` | ICP / niche / offering configuration | `validate`, `list`, `generate --json` |
| `pipeline.mjs` | Scoring, enrichment, and graph orchestration | `--status`, `--score`, `--rescore-all`, `--enrich`, `--compute-graph`, `--export`, `--health` |
| `analyze.mjs` | Read-only network analysis | `--mode <mode>` |

### api-client.mjs

Not a CLI -- a shared module imported by the other three scripts.

**Exports:**

| Export | Signature | Description |
|--------|-----------|--------------|
| `api` | `api(path, options)` | Generic fetch wrapper. Sends `Content-Type: application/json`, JSON-encodes `options.body`, throws `Error('API <status>: <message>')` on a non-2xx response. |
| `get` | `get(path)` | `GET` request |
| `post` | `post(path, body)` | `POST` request with a JSON body |
| `put` | `put(path, body)` | `PUT` request with a JSON body |
| `del` | `del(path)` | `DELETE` request |

Base URL: `process.env.NETWORKNAV_URL || 'http://localhost:3750'`.

### configure.mjs

ICP / niche / offering configuration manager. Calls `GET`/`POST` on `/api/icps`, `/api/niches`, `/api/offerings`.

```bash
node scripts/configure.mjs validate                # GET the three endpoints, report counts + warnings
node scripts/configure.mjs list                     # GET the three endpoints, print full detail
node scripts/configure.mjs generate --json '{...}'  # POST each profile/niche/offering in the JSON
```

<Callout type="warn">
There is no interactive `wizard` or `init` subcommand in v2 -- the script has no readline prompts. The `/linkedin-prospector` agent conducts the conversation itself and then calls `configure.mjs generate --json` (or the equivalent API calls directly) with the assembled config.
</Callout>

**`generate` JSON shape:**

```json
{
  "profiles": {
    "slug": { "name": "...", "description": "...", "criteria": { "roles": [], "industries": [], "signals": [], "companySizeRanges": [] } }
  },
  "niches": {
    "slug": { "name": "...", "keywords": ["..."], "industry": "..." }
  },
  "offerings": [
    { "name": "...", "description": "..." }
  ]
}
```

`generate` posts each `profiles` entry to `POST /api/icps` (as `{ slug, ...profile }`), each `niches` entry to `POST /api/niches`, and each `offerings` entry to `POST /api/offerings`. It reports created/error counts; it does not roll back partial failures.

### pipeline.mjs

Orchestrator for scoring, enrichment, and graph operations. Every flag maps to exactly one API call (`--rescore-all` also polls).

```bash
node scripts/pipeline.mjs --status                # GET  /api/dashboard
node scripts/pipeline.mjs --score [contactId]      # POST /api/scoring/run  { contactId? }
node scripts/pipeline.mjs --rescore-all            # POST /api/scoring/rescore-all, then polls GET /api/scoring/status every 2s (up to 60 attempts)
node scripts/pipeline.mjs --enrich [contactId]     # POST /api/enrichment/enrich  { contactId? }
node scripts/pipeline.mjs --compute-graph          # POST /api/graph/compute
node scripts/pipeline.mjs --export                 # GET  /api/admin/export
node scripts/pipeline.mjs --health                 # GET  /api/health  and  GET /api/extension/health-internal
```

<Callout type="warn">
`--export` requests `GET /api/admin/export`, which returns **CSV** (`Content-Type: text/csv`), and writes it out verbatim. Until 2026-08-19 the shared API client parsed every response as JSON, so this flag threw on the CSV body; it now requests a raw response for this path. Expect a `.csv` file, not JSON.
</Callout>

`--score` and `--enrich` both accept an optional contact ID as the flag's value (`--score abc123`); omit it to let the endpoint pick a target/batch.

### analyze.mjs

Read-only analysis tool with eight modes, each mapping to one `GET` request.

```bash
node scripts/analyze.mjs --mode summary                      # GET /api/dashboard
node scripts/analyze.mjs --mode hubs --top 10                # GET /api/graph/data
node scripts/analyze.mjs --mode prospects --top 10            # GET /api/contacts?sort=compositeScore&order=desc&limit=N
node scripts/analyze.mjs --mode referrals --top 10            # GET /api/contacts?sort=referralLikelihood&order=desc&limit=N (falls back to client-side sort by compositeScore)
node scripts/analyze.mjs --mode clusters                      # GET /api/graph/communities
node scripts/analyze.mjs --mode search --query "AI startup"   # GET /api/contacts/hybrid-search?q=...
node scripts/analyze.mjs --mode recommend                     # GET /api/actions/next
node scripts/analyze.mjs --mode company --name "Acme"         # GET /api/contacts?company=...
```

See [Analysis Modes](/docs/claude-agent/analysis-modes) for a full description of each mode's output.

## Common Flags

| Flag | Used By | Description |
|------|---------|--------------|
| `--mode <mode>` | analyze | Analysis mode (required) |
| `--top <N>` | analyze (hubs, prospects, referrals) | Number of results (default 10) |
| `--query <text>` | analyze (search) | Free-text search query (required for `search` mode) |
| `--name <text>` | analyze (company) | Company name to filter by (required for `company` mode) |
| `--json <string>` | configure (generate) | Full configuration JSON (required for `generate`) |

## Environment Variables

| Variable | Default | Description |
|----------|---------|--------------|
| `NETWORKNAV_URL` | `http://localhost:3750` | Base URL for the app's REST API |

## Data

There are no agent-managed data files in v2 -- contacts, scores, configuration, graph data, and vector embeddings all live in PostgreSQL, owned and served by the app. The scripts hold no state between invocations.
