# Outreach System

Outreach in v2 is owned entirely by the app (`app/src/app/api/outreach/`, `app/src/app/(app)/outreach/`) and backed by PostgreSQL. The agent has no local template engine, YAML files, or outreach state of its own -- it can call the outreach API like any other endpoint, but the templates, campaigns, and pipeline live server-side.

<Callout type="warn">
The retired v1 architecture stored templates in a local `outreach-templates.yaml` file and pipeline state in `outreach-state.json`. Those files don't exist in v2 -- templates and campaigns are database rows managed through `POST /api/outreach/templates` and `POST /api/outreach/campaigns`.
</Callout>

## Templates

```
GET  /api/outreach/templates   -- list templates
POST /api/outreach/templates   -- create a template
```

**Template fields:**

| Field | Type | Required | Description |
|-------|------|----------|--------------|
| `name` | string | Yes | Template name |
| `category` | string | No (default `custom`) | One of: `initial_outreach`, `follow_up`, `meeting_request`, `referral_ask`, `content_share`, `custom` |
| `subject_template` | string | No | Subject line template (for email-style messages) |
| `body_template` | string | Yes | Message body with merge fields |
| `merge_variables` | string[] | No | List of merge field names used in the template |
| `tone` | string | No (default `professional`) | Tone label |

## Campaigns

```
GET  /api/outreach/campaigns   -- list campaigns
POST /api/outreach/campaigns   -- create a campaign
```

| Field | Type | Required | Description |
|-------|------|----------|--------------|
| `name` | string | Yes | Campaign name |
| `description` | string | No | Campaign description |
| `status` | string | No | `draft`, `active`, `paused`, `completed`, or `archived` (default `draft`) |
| `target_count` | number | No | Target number of contacts |

Campaigns can contain **sequences** (`outreach_sequences`) made of ordered **steps** (`outreach_sequence_steps`), each referencing a template with a `delay_days` and an optional `condition`. Sequences and steps are managed in the database schema but do not yet have a dedicated top-level REST route in this guide's scope -- check `app/src/app/api/outreach/` for the current set of endpoints.

## Template Recommendation

```
GET /api/outreach/recommend?contactId=<uuid>
```

Looks up the contact's tier, persona, and referral persona from `contact_scores`, then recommends a template category:

| Condition (checked in order) | Recommended Category |
|-------------------------------|------------------------|
| Referral persona is `warm-introducer` | `referral_ask` |
| Referral persona is `white-label-partner` | `custom` |
| Tier `gold` + persona `buyer` | `initial_outreach` |
| Tier `gold` + persona `warm-lead` | `follow_up` |
| Tier `silver` + persona `hub` | `referral_ask` |
| Default | `initial_outreach` |

<Callout>
Every category this matcher can return is one the templates API accepts
(`initial_outreach`, `follow_up`, `meeting_request`, `referral_ask`,
`content_share`, `custom`). An earlier version returned four names the
`outreach_templates.category` CHECK constraint rejects, so those branches
could never match a real template and silently fell back to
`initial_outreach`, discarding the persona-specific reasoning. Fixed
2026-08-19; the mapping above reflects the current code.
</Callout>

## Pipeline (Kanban view)

```
GET /api/outreach/pipeline?campaign_id=<uuid>
```

Returns contacts grouped into Kanban-style stages, derived from the underlying `outreach_states.state` value:

| Pipeline Stage | Underlying state(s) |
|-----------------|------------------------|
| `not_started` | `not_started`, `queued` |
| `contacted` | `sent`, `opened` |
| `replied` | `replied`, `accepted` |
| `meeting_booked` | (custom state, if used) |
| `won` | (custom state, if used) |
| `lost` | `declined`, `bounced`, `opted_out` |

The underlying `outreach_states.state` column itself is constrained to: `not_started`, `queued`, `sent`, `opened`, `replied`, `accepted`, `declined`, `bounced`, `opted_out`.

## Events

Every state transition and interaction can be recorded as an `outreach_events` row (`event_type`, `event_data`), scoped to an `outreach_states` row. This is the audit trail for a given contact's outreach history.

```
GET /api/outreach/events
```

## Template Performance

`template_performance` tracks per-template, per-period counts (`sent_count`, `open_count`, `reply_count`, `accept_count`), used to compare template effectiveness over time.

## Using It From the Agent

The agent has no dedicated outreach script -- there is no `outreach.mjs`. To work with outreach data conversationally, ask `/network-intel` to call the API on your behalf, or call the endpoints directly:

```
GET /api/outreach/templates
GET /api/outreach/pipeline
GET /api/outreach/recommend?contactId=<uuid>
```

## What Changed From v1

| Capability | v1 | v2 |
|-------------|----|----|
| Template storage | Local `outreach-templates.yaml` | `outreach_templates` table, via REST API |
| Template selection | Rule table baked into the agent script | `GET /api/outreach/recommend`, server-side logic (see caveat above) |
| Pipeline state | Local `outreach-state.json` | `outreach_states` table with a full audit trail in `outreach_events` |
| Pipeline view | CLI queries against local JSON | Kanban board UI in the app (`/outreach`), plus `GET /api/outreach/pipeline` |
| Rate budgeting (`rate-budget.json`) | Config-based daily/weekly limits | No v2 equivalent found -- there is no rate-limit table or endpoint in the current schema |
| Sending | Never automated -- generate-only, human sends | Same principle holds: nothing in the API sends a message on LinkedIn on your behalf |
