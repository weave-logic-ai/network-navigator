NetworkNav deploys as two Docker containers orchestrated by Docker Compose. This guide covers setup, configuration, SSL, and production operations.

## Quick Start

```bash
# Clone and configure
cd networknav
cp .env.example .env
# Edit .env with your credentials

# Start services
docker compose up -d

# Verify health
docker compose ps
curl http://localhost:3750/api/health
```

## Local operator unlock

This Compose setup is a local-only demo: the app on port 3750 and database on
port 5432 bind to `127.0.0.1`. Before starting, set `POSTGRES_PASSWORD` and
`LOCAL_OPERATOR_SECRET` in your ignored local `.env`. Generate a fresh operator
secret with `openssl rand -hex 32` (64 hex characters), keep it out of source
and `NEXT_PUBLIC_*` variables, and do not commit `.env`.

Run `docker compose up -d`, then open
`http://localhost:3750/operator/unlock` and enter that operator secret. The
server issues an eight-hour HttpOnly, SameSite=Strict session cookie. Without
`LOCAL_OPERATOR_SECRET`, Compose refuses to start; a directly run app instead
leaves protected pages locked and returns 503 from the unlock API. The health
probe remains available.

For the Chrome extension, also set `EXTENSION_ALLOWED_ORIGINS` to the exact
installed origin, such as `chrome-extension://<32-character-extension-id>`.
Separate multiple origins with commas. An empty value denies extension-origin
requests. Extension tokens are separate from the operator session; enter the
full extension token during registration for visibility endpoints.
After unlocking, mint that token on the app's Extension page and copy it into
the extension popup. The full value is shown once; listed prefixes cannot
reconnect. Tokens expire one year after creation, so mint a replacement before
then and revoke the old token from the same page.

## Docker Compose Configuration

The `docker-compose.yml` defines two services:

### Database Service (`db`)

```yaml
services:
  db:
    image: ruvnet/ruvector-postgres:latest
    container_name: ctox-db
    ports:
      - "127.0.0.1:5432:5432"
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-ctox}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?POSTGRES_PASSWORD is required}
      POSTGRES_DB: ${POSTGRES_DB:-ctox}
    volumes:
      - ./data/db/init:/docker-entrypoint-initdb.d
      - ./data/drives/db:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-ctox} -d ${POSTGRES_DB:-ctox}"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped
```

Key points:
- Uses `ruvector-postgres` which includes the RUVECTOR extension for vector similarity search
- Schema scripts in `data/db/init/` run automatically on first start (alphabetical order)
- Data persists in `./data/drives/db/` on the host
- Health check uses `pg_isready` with 30-second start period for initial schema setup
- `POSTGRES_PASSWORD` is required; compose will fail without it

### Application Service (`app`)

```yaml
  app:
    build:
      context: ./app
      dockerfile: Dockerfile
      target: runner
    container_name: ctox-app
    ports:
      - "127.0.0.1:3750:3000"
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER:-ctox}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB:-ctox}
      NODE_ENV: production
      PDL_API_KEY: ${PDL_API_KEY:-}
      APOLLO_API_KEY: ${APOLLO_API_KEY:-}
      LUSHA_API_KEY: ${LUSHA_API_KEY:-}
      THEIRSTACK_API_KEY: ${THEIRSTACK_API_KEY:-}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY:-}
      LOCAL_OPERATOR_SECRET: ${LOCAL_OPERATOR_SECRET:?LOCAL_OPERATOR_SECRET is required}
      EXTENSION_ALLOWED_ORIGINS: ${EXTENSION_ALLOWED_ORIGINS}
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - ./data:/data
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://127.0.0.1:3000/api/health || exit 1"]
      interval: 15s
      timeout: 10s
      retries: 5
      start_period: 30s
    restart: unless-stopped
```

Key points:
- Multi-stage Dockerfile with `runner` target for minimal production image
- Waits for database health check before starting
- All API keys are optional (features degrade gracefully)
- `./data` mounted at `/data` inside the container for file access

## Environment Variables

### Required

| Variable | Description | Example |
|----------|-------------|---------|
| `POSTGRES_PASSWORD` | PostgreSQL password | `your-strong-password-here` |
| `LOCAL_OPERATOR_SECRET` | Local operator unlock secret, at least 32 characters | Generate locally with `openssl rand -hex 32` |

### Optional (with defaults)

| Variable | Default | Description |
|----------|---------|-------------|
| `POSTGRES_USER` | `ctox` | PostgreSQL username |
| `POSTGRES_DB` | `ctox` | PostgreSQL database name |
| `NODE_ENV` | `production` | Node.js environment |
| `EXTENSION_ALLOWED_ORIGINS` | empty | Comma-separated, exact Chrome extension origins; empty denies extension requests |

### Optional (API keys)

| Variable | Service | Enables |
|----------|---------|---------|
| `PDL_API_KEY` | People Data Labs | Contact enrichment (email, phone, employment) |
| `APOLLO_API_KEY` | Apollo.io | Contact enrichment (email, phone, company) |
| `LUSHA_API_KEY` | Lusha | Contact enrichment (verified email/phone) |
| `THEIRSTACK_API_KEY` | TheirStack | Company technographics |
| `ANTHROPIC_API_KEY` | Anthropic Claude | AI analysis, goal generation, template personalization |
| `CRUNCHBASE_API_KEY` | Crunchbase | Company funding and leadership data |
| `BUILTWITH_API_KEY` | BuiltWith | Company tech stack analysis |
| `ALLOW_DEV_ORIGIN` | - | Set to `true` to allow localhost CORS in production |

### Example `.env` file


## Volume Mounts and Persistence

| Host Path | Container Path | Purpose |
|-----------|---------------|---------|
| `./db/init/` | `/docker-entrypoint-initdb.d` | SQL schema scripts (read-only at init) |
| `./data/drives/db/` | `/var/lib/postgresql/data` | PostgreSQL data directory |
| `./data/` | `/data` | Application data (imports, exports) |

The `data/` directory is gitignored. Create it before first run:

```bash
mkdir -p data/drives/db data/drives/app data/drives/shared data/drives/config
```

## Health Checks

Both services expose health checks:

### Database

```bash
pg_isready -U ctox -d ctox
```

Checked every 10 seconds. The app service will not start until this passes.

### Application

```bash
wget -qO- http://127.0.0.1:3000/api/health
```

Checked every 15 seconds. Returns JSON with database connectivity status.

## SSL/TLS with Reverse Proxy

NetworkNav does not terminate SSL directly. Use a reverse proxy for HTTPS:

### Caddy (recommended for simplicity)

```
networknav.yourdomain.com {
    reverse_proxy localhost:3750
}
```

Caddy automatically provisions and renews Let's Encrypt certificates.

### Nginx

```nginx
server {
    listen 443 ssl;
    server_name networknav.yourdomain.com;

    ssl_certificate /etc/letsencrypt/live/networknav.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/networknav.yourdomain.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## Production Hardening

### Resource limits

Add to `docker-compose.yml` for production:

```yaml
services:
  db:
    deploy:
      resources:
        limits:
          memory: 2G
          cpus: "2.0"
        reservations:
          memory: 512M

  app:
    deploy:
      resources:
        limits:
          memory: 1G
          cpus: "1.0"
        reservations:
          memory: 256M
```

### Restrict database access

In production, remove the database port mapping to prevent external access:

```yaml
services:
  db:
    # Remove or comment out:
    # ports:
    #   - "5432:5432"
```

The app service connects to the database via Docker's internal network (`db:5432`).

### Restart policies

Both services use `restart: unless-stopped`, which restarts containers after crashes or host reboots but not after manual `docker compose stop`.

## Backup and Restore

### Database backup

```bash
# Backup to compressed SQL
docker exec ctox-db pg_dump -U ctox -d ctox | gzip > backup-$(date +%Y%m%d).sql.gz

# Or use pg_dump with custom format for parallel restore
docker exec ctox-db pg_dump -U ctox -d ctox -Fc > backup-$(date +%Y%m%d).dump
```

### Database restore

```bash
# From SQL
gunzip -c backup-20260319.sql.gz | docker exec -i ctox-db psql -U ctox -d ctox

# From custom format
docker exec -i ctox-db pg_restore -U ctox -d ctox --clean < backup-20260319.dump
```

### Full system backup

```bash
# Stop services first for consistent backup
docker compose stop

# Backup data directory
tar czf networknav-backup-$(date +%Y%m%d).tar.gz data/

# Restart
docker compose up -d
```

### Automated backups

Create a cron job for daily backups:

```bash
# /etc/cron.d/networknav-backup
0 2 * * * root docker exec ctox-db pg_dump -U ctox -d ctox | gzip > /backups/networknav-$(date +\%Y\%m\%d).sql.gz
```

## Upgrading Schema

New SQL migration scripts are added to `data/db/init/` with incrementing numeric prefixes. These only run on first database initialization. A copied or existing volume can be missing older migrations even when newer tables exist; check required tables and columns rather than assuming the highest filename was applied.

For existing deployments, apply migrations manually:

```bash
docker compose exec -T db psql -U "${POSTGRES_USER:-ctox}" -d "${POSTGRES_DB:-ctox}" -v ON_ERROR_STOP=1 -1 < data/db/init/019-referral-scoring-schema.sql
```

Or connect directly:

```bash
docker exec -it ctox-db psql -U ctox -d ctox
```

### Graph grouping upgrade

Migrations 059 and 060 run automatically only when PostgreSQL initializes a **new** volume. On an existing volume, stop graph Compute requests and back up that database from the repository root:

```bash
mkdir -p data/drives/backups
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "data/drives/backups/graph-upgrade-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

Confirm that every applicable earlier migration has been applied to this specific database. This checkout has no 057 or 058 scripts; if your deployment supplies them from another release, resolve those dependencies before applying 059/060. A copied volume can have gaps, so check its schema rather than relying on the latest filename. In particular, `cluster_memberships` must exist before 059. Apply 059 then 060 together from the repository root, using the Compose project for the intended deployment (do not substitute a different project's database):

```bash
cat data/db/init/059-cluster-membership-count-index.sql data/db/init/060-graph-compute-publication.sql | \
  docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -X -v ON_ERROR_STOP=1 -1'
```

The `-1` flag wraps both scripts in one transaction and `ON_ERROR_STOP` exits on failure. Do not enable Compute until this verification returns one index, one state table, and exactly one state row. Its graph pointer remains empty until the first successful Compute; the legacy `contacts` graph may contain extra relationship types and is not a publication:

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -X -v ON_ERROR_STOP=1 -c "SELECT to_regclass('\''public.idx_cluster_memberships_cluster_id'\'') AS membership_index, to_regclass('\''public.graph_compute_state'\'') AS publication_table, (SELECT count(*) FROM graph_compute_state WHERE id = TRUE) AS pointer_rows"'
```

If either object is absent, the graph data and Compute APIs return HTTP 503 with this upgrade path. If the pointer row is missing, repair the interrupted 060 migration before retrying. Once verified, restart the app. A failed migration rolls back both scripts; fix the reported prerequisite and rerun the same idempotent scripts. Keep the backup until graph data loads and Compute succeeds.

### Isolated local demo

The repo's demo override keeps database and app-data volumes separate from the default stack and binds the app to localhost on port 3751:

```bash
docker compose -f docker-compose.yml -f data/config/docker-compose.demo.yml -p network-navigator-demo build app
docker compose -f docker-compose.yml -f data/config/docker-compose.demo.yml -p network-navigator-demo up -d
curl http://127.0.0.1:3751/api/health
```

The two stacks share the built image name, but their containers and volumes are distinct. To stop the demo while retaining its data, use the same Compose arguments with `stop`. Avoid `down -v` unless you intend to discard the demo volumes.

For an **existing** demo volume, init scripts do not rerun. Review the pending SQL against that volume before applying it. For example, after checking `research_target_icps` and backing up the database, apply migration 053 transactionally from the repo root:

```bash
docker compose -f docker-compose.yml -f data/config/docker-compose.demo.yml -p network-navigator-demo exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -1' < data/db/init/053-lens-icp-canonical.sql
```

The local demo copy used for research-tool validation also lacked parts of migrations 018 and 019. Those were reconciled additively before scoring and dashboard checks; this is a reason to audit any copied volume before treating it as release evidence.
