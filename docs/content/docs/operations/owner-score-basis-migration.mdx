# Owner Score Basis Cutover (058)

`data/db/init/058-owner-score-basis.sql` runs automatically only on a new PostgreSQL volume. Apply it manually to an existing volume after migrations 056 (identity repair uniqueness) and 057 (target state revision). Migration 056 is integrated at commit `777ef5c` (SHA-256 `3ed69a3b3f374730b54fce82e08b82c3268fd7f44ef4ee9afa1e75db08106b1c`); 057 must also be integrated before deploying 058. The proof used the project's `ruvnet/ruvector-postgres:latest` image and PostgreSQL 17.9, not the demo database.

The context-preview pipeline calls `getActiveLensForTarget(targetId, { tenantId, ownerId }, client)` within its read-only snapshot. The lens service scopes the read to that owner and tenant, and the pipeline checks the returned lens against the current owner and requested target before reading ICPs. Apply migration 057 before 058.

Before rollout, stop every app instance and background score writer, take a full database backup, and confirm the replacement app is ready. An old app cannot write `contact_scores` after 058: the database trigger rejects writes without the transaction-local owner-writer marker and owner basis metadata. Do not roll only the app back to an old version while keeping 058.

Apply each predecessor and then 058 with `psql -X -v ON_ERROR_STOP=1 -f <migration-file>` against the intended database. `058` is wrapped in one transaction. Afterward, verify the columns and pending queue index exist, and that retained rows have `basis_kind = 'legacy-unverified'` and `basis_hash IS NULL`. A score remains unverified until the new owner pipeline replaces it. The first replacement stores the prior row and dimensions in `score_context_legacy_backups` in the same transaction. For a large retained volume, run the new Rescore All operation after cutover and monitor completion; do not relabel historical scores as owner scores in SQL.

Owner ICP membership is the explicit `icp_profiles.owner_baseline` flag. Migration 058 sets it for active profiles with **no target ICP association at all** and for the natural ICP. Legacy lens templates use unscoped target associations, so they remain out by default, as do scoped lens profiles. Review shared profiles and opt them in deliberately. New global ICP creation sets the flag; lens-only creation leaves it false. Changing a lens-only ICP cannot change the owner score basis hash or the Rescore All basis.

The legacy graph importer always keeps contacts and source signals and ignores precomputed scores. With `rescore=true`, it commits a `score_import_jobs` row and its contact ledger **in the same transaction as the source data**. It returns `rescoreJobId`; scoring then proceeds in bounded passes. The first pass stores an immutable owner basis in the job. Each contact score and ledger completion commit together, so an interruption leaves unfinished contacts for the startup worker and its 30-second sweep. With `rescore=false`, no score job is created. Monitor `score_import_jobs.completed_at`, `score_import_job_contacts.scored_at`, `skipped_at`, `attempts`, and `last_error`. Archived contacts become terminal skips; other failures rotate behind untried contacts and remain pending for retry.

Migration 056 owns `uq_tasks_pending_auto_recommendation` and limits it to `SEND_MESSAGE`, `RESEARCH`, and `ENGAGE_CONTENT`; 058 leaves that index unchanged. Notification tasks use `impulse_notification_tasks` to deduplicate retries of one impulse while allowing distinct impulses for the same contact. If a notification task is deleted, its ledger row remains as a tombstone so a retry does not recreate it. The worker reuses successful handler acknowledgments. External webhook delivery remains **at-least-once**: a send can succeed and the process can fail before its success acknowledgment is recorded. A retry uses the same `Idempotency-Key` (`impulseId:handlerId`), but only a receiver that enforces that key can prevent duplicate external effects. Webhook handlers are opt-in; the shipped seed does not enable one.

`score_contact_revisions` records the last committed revision per surviving contact. A scoring purge may delete `contact_scores` while leaving older impulses; the next owner write advances the ledger instead of reusing revision 1. Contact deletion cascades the ledger. Do not manually reset this counter while any score or scoring impulse for the contact remains.

Consumers may compare score deltas only when **both** rows have `basis_kind = 'owner'`, both hashes are non-null, and their `basis_hash` values match. A matching `scoring_version` alone is insufficient. The hash includes captured owner ICP criteria, weights, taxonomy-derived criteria, referral baselines, and the algorithm version. Snapshot IDs identify the capture transaction but are not durable semantic revisions.

For a bounded per-contact rollback, stop writers and invoke `SELECT restore_legacy_contact_score('<contact-uuid>');` inside a transaction. It returns false when no backup exists. The function restores the saved legacy score and dimensions, invalidates its owner basis, and deletes only pending scoring impulses for that contact. **It does not reverse tasks, webhook deliveries, campaign effects, or impulses already marked dispatched.** It also leaves the score revision counter intact. A fleet rollback requires the full pre-cutover database backup and a coordinated app rollback; do not drop the guard trigger while the new app can still write.

Disposable proof: exact schema files 001–055, then 056, 057, and 058 applied cleanly to a fresh database and a second database containing a retained version-1 legacy score with score and referral dimensions. On the retained database, the row kept `legacy-unverified`/null hash, an old-style update failed with SQLSTATE 42501, a guarded owner replacement preserved a backup, and `restore_legacy_contact_score` restored the original 95/gold score and both dimensions. A task and a marked-dispatched impulse deliberately survived restore; a pending impulse was removed. The disposable PostgreSQL scoring fixture also covers atomic scoring, concurrent replacement, ordered replay, bounded recovery, import-job restart, notification deduplication, and webhook acknowledgment failure/retry.
